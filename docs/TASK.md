## 0. 軸 — 進め方の方法論(全フェーズ共通)

過去の重大バグ(カード効果ID・クエスト完了E3・攻撃ミラーのnSkillID)の反省から、
実装は必ずこの順で行う:

1. **逐語移植** — パケットの中身・送信タイミングは自作しない。リファレンス
   (Reference/JMSv186 の `ReqC*` → 送信呼び出し)の該当箇所を読み、呼び出し構造ごと
   移植する。「たぶんこう」で書いた箇所が全クラッシュの原因だった。
2. **契約監査** — 「リファレンスが送らない場面で送っていないか / 送る場面で
   送り忘れていないか」を机上で突き合わせる(フェーズ1)。
3. **差分検証** — 解析で決まらないものだけ検証に回す。ラウンドトリップテスト(自動)、
   golden vector(`CRONUS_BOT_CAPTURE` でJavaオラクルと比較)、実機二分探索(最終手段)。
4. **実機確認** — クライアント状態を壊しうる変更(ダイアログ・クエスト・インベントリ・
   フィールド遷移・エフェクト)は実クライアントで一度は踏む。

**解析だけで完結しない理由**(必ず覚えておく):
- リポジトリ自体が**v186では未検証の箇所がある**(Riremito氏いわく147/187が最良。
  カード効果ID=16はリポジトリのどこにも無く、実機二分探索でのみ判明)
- **多バージョン分岐**(v131〜302同居)の読み違えはコンパイラが検出しない
- **転記ミス**は自分では気付けない(完了時E3事件)

**オラクルの使い分け**:
| 質問 | 使うもの |
|---|---|
| パケットのバイト配置は? | `ResC*`/`Data*` クラス(逐語移植) |
| いつ・何を送る? | `ReqC*` ハンドラの呼び出し構造 |
| enum/効果IDの値は? | `Ops*` の `init()` のJMS186分岐。**無ければ疑う**(宣言デフォルトはGMS v95) |
| データの意味は? | gamedata.db(=クライアントと同一) + Java側 `Wz*` ローダ |
| どうしても決まらない | Javaオラクル起動+bot capture / 実機 `/booktest` 式二分探索 |

## フェーズ1: パケット契約監査(最優先・進行中)

今回型のクラッシュ(送信タイミング契約のズレ)を机上で先取りする。
リファレンスの各ハンドラとうちの `ChannelHandler.*` を突き合わせ、
**送る/送らない/順序** の差を全部洗う。クライアント状態を壊しやすい系から。

- [x] クエスト (`UserQuestRequest`) — 完了時E3は nextQuest 時のみ・記録が先 (e1cdb92)
- [x] NPC会話 (`UserSelectNpc` / `UserScriptMessageAnswer` / ScriptMessage の全型)
      — 監査結果: 応答デコード(menu=int/text=str/avatar=byte/slide=int・ESC意味論)は一致。
      **修正2件**: ①ショップ/倉庫を開いている間のNPCクリックを拒否(oracleの会話ロック相当)
      ②マップ移動時に shop/storage/会話状態をクリア(ロック残留防止)。
      **休眠ギャップ**(未使用のため未修正・使う時に直す): SM_SAYIMAGE のcountバイト、
      SM_ASKNUMBER/QUIZ系のペイロード(現行スクリプトAPIに無い)
- [x] フィールド遷移 (`UserTransferFieldRequest` / `UserPortalScriptRequest` / 死亡復帰)
      — 監査結果: 失敗時 `TransferFieldReqIgnored` は転送要求側では実装済みだった。
      **修正2件**: ①ポータルスクリプト要求の失敗(未知ポータル/スクリプト無し/エンジン無効)が
      無応答だった → 拒否パケットで排他ロックを解除 ②死亡復帰の `revive_type` を解釈
      (>0 = その場復活、0 = 帰還マップ。HP/MP全快は一致済み)。
      在マップテレポート(`PortalTeleportRequest`)はoracle自体が not coded — 未対応でOK。
      MigrateIn/チャンネル移動は実機で常用済みのため対象外とした。
- [x] インベントリ 排他ロック解除の全パス監査 — oracleの規則「失敗も必ず `updateInv()`
      (空InventoryOperation) か StatChanged で応答」に対し、**沈黙分岐11箇所を修正**:
      アイテム使用(死亡中/desync/帰還先なし)、スクロール(desync/回数切れ/対象違い)、
      スロット移動(装備間移動拒否/空スロット)、地面ドロップ(空スロット)、
      拾得(死亡中/取得済み)。バフ解除は oracle 同様 **常に** TemporaryStatReset を返すよう変更。
      機械走査ツール: 早期returnの直前5行に応答packetが無い分岐を列挙する方式(再利用可)。
      残り(InventoryOperation 全モードのバイト検証・Gather/Sort応答)は golden vector 拡張時に。
- [x] ショップ (`UserShopRequest` 各op) — v186表(Close=4・結果0-12)は一致、
      buy/sell/rechargeの失敗コードも一致。**バグ修正1件**: リチャージ品(手裏剣・弾)の購入は
      oracleでは「定額でスタック満タン」なのに価格×個数・個数分付与になっていた。
      **軽微修正1件**: 補充要求が既に満タンの場合に無応答だった → RechargeUnknown で応答
      (oracleは未定義enumを送る箇所のため、定義済みコードを選ぶ意図的な差)。
      ペット購入のペットインスタンス生成は未対応(NPC店でのペット販売なし、キャッシュ側は対応済)。
- [x] 倉庫(Trunk) — 預入/引出/メルの失敗は TrunkError(PutNoMoney/IncorrectRequest/NoSpace等)で
      全分岐応答済みを確認。ショップ/倉庫とも「開いていない状態の要求は沈黙」も oracle と一致。
- [x] トレード・ミニゲーム・個人商店(ルーム系) — 入室失敗は全経路 MiniGameFull で応答済み。
      ルーム内操作(put/buy等)の失敗は **oracle自身がほぼ沈黙**(ReqCMiniRoomBaseDlg)であり、
      うちの沈黙分岐は契約一致と判定。差分なし。
- [x] スキル・バフ — ackが先(SkillUseResult)・バフ順・cooldown・パーティバフは一致。
      **修正3件**: ①未習得/効果なしスキルのキャスト後に StatChanged 空アンロックを送る
      (oracleの sendStatChanged(true) 相当) ②スキルキャンセルの周囲通知 `LP_UserSkillCancel`
      を新規実装(未送信だったため他人視点でオーラが残っていた)③ポータルスクリプト起動前の
      効果音 PlayPortalSE=10 を送出(v302表−1の法則、**実機検証済み 2026-08-26**)。
      残メモ: MP不足でもバフが掛かる(サーバー権威の締め付けはフェーズ4で)。
- [x] 戦闘・被弾 — 攻撃ミラー(nSkillID/keydown/メソ爆発)は修正済み。今回:
      **被弾ミラー `LP_UserHit` が未実装だった**のを発見・移植(oracleは全被弾分岐で
      無条件ブロードキャスト — 他人の被ダメ数字・仰け反りが今まで一切見えていなかった)。
      CP_UserHit のフルデコード(v186 攻撃index表: Magic=0/Physical=-1/Obstacle=-2/
      Stat=-3/Counter=-1000、Mob攻撃ブロック、障害物short)も併せて移植。MISS(0)も
      ミラーする。fake-skill(-1)形はレジストリ未保持のため未対応(oracleもhack扱い)。
      被弾HP適用・死亡ペナルティ・パーティ通知は既存どおり。ミラーはテストでピン留め。
      残: deadlyAttack/mpBurn/mob状態異常スキル適用はフェーズ4(状態異常系)とセット。
- [x] ソーシャル — パーティは失敗を PartyResultSimple のエラーコードで全応答済み、
      バディも FriendSet* コード実装済み、ギルドのUI可視失敗(本部要件/満員/メル不足)は
      通知で応答済みを確認。沈黙分岐は権限/整合性ガード(正規クライアントは送らない)のみ。
      **修正2件**: ①キャッシュアイテム使用(拡声器・黒板)の失敗3経路が無応答だった →
      oracleのdispatcher契約(`!handled → updateInv`)どおり空InventoryOperationで解除
      ②ペットフードのdesync失敗も同様に解除。
- [x] キャッシュショップ — 入退場はbot往復で実証済み、購入/ロッカー移動の失敗は
      FailResult(NoStock/NoRemainCash/NoEmptyPos)で全応答済みを確認。差分なし。

**フェーズ1完了(2026-08-25)**: 10系統の監査で修正21件+リチャージ購入バグ+被弾ミラー移植。
今後の新ハンドラは「軸」の手順(逐語移植→契約確認)を踏むこと。

**やり方**: 系ごとに (1) リファレンスの送信呼び出しを列挙 → (2) うちの同じパスの送信を列挙 →
(3) 差分を表にして判定(意図的な差か・バグか)→ (4) 修正+テスト → (5) この表にチェック。
発見した差分は監査メモとしてコミットメッセージに残す。
